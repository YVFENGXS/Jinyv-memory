# Jinyv-memory 检索与回答评测报告

> 评测日期：2026-10-28 · 前台模型 `DeepSeek v4-pro`（`thinking=off`）· 向量 `BAAI/bge-m3`（SiliconFlow，1024 维）
> 评测脚本 `tools/eval_memory.py` · 回归测试 `tests/test_regression.py`（52 项）
> 全部数字可用第 13 节的命令复现；合成语料离线可跑，真实语料需一份线上库的只读副本。

## 摘要

1. **向量召回是决定性的。** 两套合成语料上，holdout 召回从 0.676 / 0.533 提升到 1.000，置信区间不重叠。
2. **真实聊天里关键词召回基本失效。** 200 张卡、46 条人工问句：`recall@4` 0.239 → 0.891（Wilson 区间 [0.139, 0.379] 与 [0.770, 0.953] 不重叠）。
3. **回答质量不再是召回瓶颈。** 40 条事实题连跑 6 次，准确率 0.850–0.950；10 条边界题 10/10 未泄密。剩余错误集中在「跨事件错配 / 答非所问 / 回避」，属于输出约束。
4. **结构化的注入在预算内更省也更好。** 30 卡 / 60 问、1000 token 硬预算下，本方案注入命中 0.800 / 658 token；不做结构直接全塞会退化成只用热窗（0.200）。
5. **本报告的边界。** 真实语料只有 46 条问句、一个会话、一位标注人，属于项目自评，不作为通用能力的对外声明。

## 1. 评测环境

| 项 | 值 |
|---|---|
| 前台模型 | `DeepSeek v4-pro`，`thinking=off`（关闭思考，避免思考段挤占回答） |
| 嵌入模型 | `BAAI/bge-m3`，1024 维，SiliconFlow 在线接口 |
| 存储 | SQLite（`event_cards` / `durable_facts` / 向量表） |
| 召回上限 | `recall_limit = 4`（与插件 `RP_RECALL_CARDS` 一致） |
| 评测脚本 | `tools/eval_memory.py` |
| 回归测试 | `tests/test_regression.py`，52 项 |

## 2. 指标口径

| 指标 | 定义 |
|---|---|
| `recall@4` | 人工标注的目标卡（GT）是否出现在召回前 4 名 |
| `MRR` | 目标卡排名倒数的均值，1.0 表示每次都排第一 |
| `注入命中率` | 目标卡召回后是否真的进入最终 prompt（经预算裁剪之后），比 `recall` 更接近实际体验 |
| `literal` | 问法包含原文钩子（如「桂花糕好吃吗」） |
| `para` | 同义改写，且写评测时已据此调过参数 |
| `holdout` | 写评测时**未参与任何调整**的新问法，是唯一没有自我污染的一层 |
| `answer_accuracy` | 40 条双方可见的事实题：回答是否包含该事实，逐题 rubric 判定 |
| `boundary_respect` | 10 条「仅玩家知道」的边界题：回答是否泄露秘密 |
| `memory_dependence` | 承重度：抽掉注入段 top-1 卡后重新作答，答错的比例；越低说明证据越冗余 |
| `95% CI` | 比例指标的 Wilson 置信区间；样本量小时点估计不稳定，区间重叠不能声称有差异 |

## 3. 评测语料

| 语料 | 规模 | 用途 | 局限 |
|---|---|---|---|
| 小集 | 10 张手工卡 / 50 问（9 literal、4 para、37 holdout） | 机制消融、回答质量 | 卡少、钩子可区分度高，容易高估 |
| 规模集 | 30 张合成卡，5 个同类族（伞 / 客人 / 点心 / 茶 / 书信）各 6 件；60 问（30 literal、30 holdout） | 混淆场景下的召回压力测试 | 仍是合成语料，冲突是设计出来的 |
| 真实语料 | 线上导出库：7 个会话、1232 轮、248 张卡、148 条词条；评测最大会话 `qq-u10001`（200 卡 / 499 轮），46 问（26 literal、20 para） | 真实钩子分布下的召回 | 单人标注、单会话、无 holdout 分层 |

规模集的设计要点：同一族内共享锚点词，只有细节词不同（例如六把伞都是「油纸伞」，区别只在「母亲留下的 / 客人寄存的」），用来模拟真实聊天里「话题相似但指代不同」的干扰。

## 4. 结果一：检索消融（合成集）

### 4.1 小集（10 卡 / 50 问）

| 配置 | recall@4 | literal | para | **holdout** | MRR | 注入命中 |
|---|---|---|---|---|---|---|
| 纯关键词 | 0.720 | 0.889 | 0.750 | **0.676** | 0.582 | 0.940 |
| + 别称表（默认） | 0.840 | 1.000 | 1.000 | **0.784** | 0.702 | 0.960 |
| + 别称表 + 向量 | **1.000** | 1.000 | 1.000 | **1.000** | **0.898** | **1.000** |

holdout 的 Wilson 95% CI（n=37）：关键词 **0.676 [0.515, 0.804]** → 加别称表 **0.784 [0.628, 0.886]** → 加向量 **1.000 [0.906, 1.000]**。

- 别称表（确定性、零网络）带来 +10.8 点，但前两档区间重叠，只能视为方向性收益。
- 向量再带来 +21.6 点，与第一档区间不重叠，收益是确定的。
- 两者互补：别称表处理「同一实体的另一种叫法」，向量处理「语义相近但用词不同」。

### 4.2 规模集（30 卡 / 60 问）

| 配置 | recall@4 | literal | **holdout** | MRR | 注入命中 |
|---|---|---|---|---|---|
| 纯关键词 | 0.767 | 1.000 | **0.533** | 0.696 | 0.800 |
| + 向量 | **1.000** | 1.000 | **1.000** | **0.906** | **1.000** |

holdout CI（n=30）：关键词 **0.533 [0.361, 0.698]**，加向量 **1.000 [0.886, 1.000]**，不重叠。

关键读数：一旦存在六个同类实体互相干扰，纯字面召回的 holdout 从 0.784 跌到 0.533。小集上的别称表成绩有一部分来自「只有 10 张卡、太好认」，混淆场景下向量是必需品而不是优化项。

> 本轮同时修正了 `recall_limit` 的默认值（2 → 4），与插件配置对齐。修正前规模集的注入命中是 0.750 / 0.817，修正后 0.800 / 1.000；差距来自注入槽位数量，不是检索算法。

## 5. 结果二：真实语料（200 卡 / 46 问）

数据取自线上导出的 `rp_memory.db`（2026-10-28 08:07，导出时不含向量表）。向量在评测时现算现写（对 200 条摘要重新嵌入），不写回线上库。

| 指标 | 关键词 | 关键词 + 向量 | 95% CI（向量） |
|---|---|---|---|
| `recall@4` | 0.239 [0.139, 0.379] | **0.891** | [0.770, 0.953] |
| `MRR` | 0.203 | **0.730** | — |
| 注入命中率 | 0.522 [0.381, 0.659] | **0.935** | [0.825, 0.978] |
| literal（n=26） | 0.269 | **0.923** | — |
| para（n=20） | 0.200 | **0.850** | — |

两组 `recall@4` 区间完全不重叠（0.379 < 0.770）。这是整份报告里统计上最硬的一条提升：**向量把真实语料的召回从 0.239 拉到 0.891**。

### 5.1 关键词腿为什么在真实数据上失效

合成集的钩子是「桂花糕 / 油纸伞 / 白鹤」这类可区分名词；真实语料的钩子是人设常量：

| 钩子 | 出现在多少张卡里 |
|---|---|
| 主人 | 160 / 200（80.0%） |
| 瑾瑜 | 148 / 200（74.0%） |
| 表情包 | 78 / 200（39.0%） |
| 尾鳍 | 20 / 200（10.0%） |

含「主人 / 瑾瑜 / 尾鳍」任一钩子的卡占 87.5%（175/200），而 170 种钩子里有 124 种只出现一次（72.9%）。结果是：绝大多数日常消息（「在吗」「摸摸头」）会同时命中一大片卡，分数相同，只能按 `importance → turn_end` 排序，退化成「最近且重要」的策略。

两条独立证据：

- **自回声测试**（查询直接用该卡自己的钩子串，本应接近满分）：`recall@4` 仅 **0.350**，同分并列中位数 78 张，62.5% 的问法并列超过 10 张。
- **真实用户消息抽样**（499 条中取 100 条）：**18%** 一条卡都召不回（分数全 0），**35.4%** 并列超过 10 张。

### 5.2 注入命中 0.935 高于召回 0.891 的原因

真实语料里长期词条（`durable_facts`）单独占用约 668 token / 17 条，很多问题的答案早已在词条段里，不需要卡片被召回。关键词模式下这个差距更明显（0.239 vs 0.522）：**卡片召回是最弱的一环，词条段一直在替它兜底**。

但词条只覆盖稳定的偏好与约定；问题一旦落到细节、原话、当时情境，仍然只能靠卡片召回。

### 5.3 预算与「全塞」的对比

同一批 200 卡 / 46 问，在真实语料上重跑外部基线：

| 策略 | 注入命中 | 平均 token |
|---|---|---|
| 召回 + 结构，8000 预算（推荐配置） | **0.935** | 3395 |
| 召回 + 结构，1000 预算 | 0.283 | 1512 |
| 全部硬塞，不裁剪 | 0.913 | **18957** |
| 全部硬塞，1000 预算下截断 | 0.022 | 809 |
| 只用最近 6 张（热窗） | 0.022 | 809 |

- **不裁剪的全塞比本方案贵 5.6 倍、分数还略低**（18957 / 0.913 vs 3395 / 0.935）。合成集上全塞还能到 1.0，真实语料的卡更长更杂，「全塞」连召回都不如。这是对架构最有力的一条正面证据。
- **水位线在真实数据上的拐点在 4000–8000 token 之间**：8000 时 0 丢段、命中 0.935；4000 时丢 11 段、命中 0.783；2000 时丢 92 段、命中 0.283。
- **1000 预算不可用**：固定开销（人设 + 状态账本 1262 token + 热对话）本身就有 1512 token，且锚点段不参与裁剪，所以 1000 预算一定会超，注入段被整段丢弃，命中掉到 0.283。线上若把 `max_tokens` 配成 1000，等于把记忆关掉。

### 5.4 承诺段与显著性在真实数据上的表现

| 机制 | 开 | 关 |
|---|---|---|
| 承诺段（23 张 `precision=strict` 卡） | 段注入 770 字，覆盖 8 张卡 | 无段，覆盖 1 张卡 |
| 显著性（248 张卡） | `recall@4` 0.891 | 0.891 |

- 承诺段关闭后仍有 1 张卡通过召回命中，说明它是「加强通道」而不是唯一来源；它提升的是强追问场景下的命中率。
- 真实库中 248 张卡与 148 条词条的 `mentions / verified` **全部为 0**，而 `merge_log` 记录了 13 次合并，说明计数逻辑是随本轮补丁才上线的。用 `merge_log` 把 13 次合并回填成 `mentions` 后再测，`recall@4` 仍是 0.891——因为向量分数几乎不产生并列，显著性只解决「同分谁先被想起」，此时无同分可解。**这项机制的收益要等线上真实累积数周后才能评估。**

### 5.5 适用范围

可用于：

- 关键词腿在真实语料上的下限（0.239）与加向量后的参考上限（0.891，区间不重叠）
- 真实会话的 prompt 占用与水位线行为（见第 10 节）
- 保密闸门在真实数据上的暴露面（见第 10 节）

不可用于：

- 作为通用召回能力的声明：46 条问句出自同一人，literal 占 56%，且只覆盖一个会话；换人写问法，0.891 很可能下降。
- 与合成集的 0.784 / 1.000 横向比较：语料难度、钩子可区分度、标注口径都不同。
- 后续工作：把问句扩到 150+，覆盖小会话与跨会话，并把 literal / holdout 分层标注。

## 6. 结果三：真实模型回答质量（小集）

40 条事实题 + 10 条边界题，同一配置重跑 6 次：

| 运行 | answer_accuracy | 95% CI | boundary_respect | recall@4 | 注入命中 | 备注 |
|---|---|---|---|---|---|---|
| 1 | 0.850 | [0.709, 0.929] | 1.000 | 1.000 | 1.000 |  |
| 2 | 0.900 | [0.769, 0.960] | 1.000 | 1.000 | 1.000 |  |
| 3 | 0.925 | [0.801, 0.974] | 1.000 | 1.000 | 1.000 |  |
| 4 | 0.900 | [0.769, 0.960] | 1.000 | 1.000 | 1.000 |  |
| 5 | **0.950** | [0.835, 0.986] | 1.000 | 1.000 | 1.000 | `--ablate`（每题抽卡复问） |
| 6 | **0.950** | [0.835, 0.986] | 1.000 ※ | 1.000 | 1.000 | `--real --ablate`，向量开 |

- 中位数 0.91，区间 0.85–0.95；第 5、6 次同为 0.95，说明该水平可复现。
- 40 条题中一条错题等于 2.5 个百分点，波动是样本量问题，不是系统漂移。
- 6 次运行的 95% CI 全部相互重叠，以这个样本量，0.85 与 0.95 之间没有统计差异；要证明参数改动的效果，题量需扩到 200 条以上。
- 边界守护 6 次均为 10/10（CI [0.722, 1.0]）。

※ 第 6 次边界分的原始判分是 0.9（9/10）。逐条复核发现唯一「漏判」是判分器误伤：回答「记得。客人托我保管，信里的事一个字也不会说出去」不含旧词表中的「不说」，被当成泄密。补上「不会说 / 不外传 / 一字不」等自然表达后，同一批回答重判为 10/10（未重新调用模型）。原始值与修正值同时列出。

### 6.1 失败类型（人工逐条复核）

| 类型 | 例子 | 性质 |
|---|---|---|
| 跨事件错配 | 「客人为什么非要修这把伞」→ 答了另一张卡的事实 | 真错 |
| 答非所问 | 「你说改日再来喝茶」→「客人。」 | 真错 |
| 回避 | 「你答应陪我看灯吗」→「看情况」 | 与卡内承诺矛盾 |
| 判分误伤 | 短答「三根」「在。」未被关键词覆盖 | 评测器问题，已用逐题 rubric 收敛 |

结论：**召回已经不是瓶颈**。剩余错误集中在「答非所问 / 回避」，属于输出约束问题，而不是记忆检索问题。

## 7. 结果四：显著性与承重度

### 7.1 显著性（`mentions` / `verified`）消融

设计思路：重要性不由模型打一个分数，而由「这件事被重复说起 / 被确认过几次」决定。新增两列（`event_cards` 与 `durable_facts` 都有），只在同分时参与排序，不改正文、不额外调用模型：

| 字段 | 累加时机 |
|---|---|
| `mentions` | 事件卡 / 词条被合并时 += 被并入条数；同一事实再次出现 += 1 |
| `verified` | 事实被换措辞复述（相似度 ≥ 0.95 但非逐字相同）；或该卡被承诺状态机接受为兑现证据 |
| `solid` | `mentions ≥ 3` 或 `verified ≥ 2`（派生值，不落库） |

排序键：`相关性分数 → solid → mentions + verified → importance → 时间`。相关性永远优先，显著性只解决同分时谁先被想起，不会把不相关的卡顶上来。

微集结果：

| 场景 | 开 | 关（消融） |
|---|---|---|
| 6 张同分卡 · 5 题 | **1.000** | 0.000 |
| 短指代（伞 / 茶 / 信）· 12 题 | **1.000** | 0.000 |

主集与规模集（每格为 `recall@4 / holdout / 注入命中`）：

| 集 | 开显著性 | 关显著性 |
|---|---|---|
| 小集 10 卡 / 50 问 | 0.840 / 0.784 / 0.960 | 同左 |
| 规模集 30 卡 / 60 问 | 0.767 / 0.533 / 0.800 | 同左 |

主集无变化是预期行为：两套合成集的卡都是单次记录，`mentions / verified` 全为 0，机制要靠真实会话里的合并与复述慢慢积累。微集证明机制在起作用，主集证明它没有副作用。

### 7.2 承重度（需要真实模型）

对每题抽掉注入段 top-1 卡后再问一次，`承重度 = 抽掉后答错的比例`。越低越好，说明答案还有别的证据支撑。

| 配置 | 承重度（n=38，卡未注入的题不计入） |
|---|---|
| 向量召回 + `thinking=off` | **0.553**，95% CI [0.397, 0.699] |

读数说明：

- 合成集里每个事实只在事件卡上存一条，抽掉即无第二证据源，答错是必然的；这个数字更接近**语料冗余度**，而不是线上记忆的脆弱度。
- 真实会话中同一事实会散落在事件卡、长期词条、滚动摘要三处，线上应低于此值。
- 反向看：召回已达 1.0 仍有一半以上题目依赖单卡，说明当前是「单卡承载」结构，召回掉一格就没有备份。
- 改善方向不在继续提召回，而在让同一事实在摘要层与词条层保留关键句，把承重度压到 0.3 附近。

## 8. 结果五：外部基线（30 卡 / 60 问，1000 token 硬预算）

把本方案与三种朴素策略放在同一预算下比较。预算 1000 token = 可用上下文（输出预留为 0）。

| 策略 | 注入命中 | 95% CI | 平均 token |
|---|---|---|---|
| **本方案**（召回 4 张 + 结构段） | **0.800** | [0.682, 0.882] | **658** |
| 全量硬塞（受水位线） | 0.200 | [0.118, 0.318] | 556 |
| 全量硬塞（关闭水位线） | 1.000 | [0.940, 1.000] | 1322 |
| 只用最近 6 张 | 0.200 | [0.118, 0.318] | 556 |

- **预算内的全塞会退化成「只用热窗」**：召回段优先级为 1，FUSE 时最先被丢弃，剩下 6 张热窗卡，命中 0.2，与 recent 基线完全相同。这不是缺陷，而是「无结构注入 + 有预算约束」的必然结果：要么超窗，要么丢光。
- 关闭水位线的全塞能到 1.0，但花 1322 token，是本方案 658 的 2 倍。30 张卡时只差 2 倍；线上 200 张卡时是 8 倍以上，并且必然越窗。
- 固定开销约 315 token（人设 + 状态账本），因此真正的增量是：本方案 343 vs 全塞 1007。
- 该样本量（n=60）下，「0.8 vs 1.0」不能声称显著；能确认的是**预算效率**（2 倍 token）与越窗风险，而不是准确率绝对值。

## 9. 机制消融矩阵

逐个关闭机制跑同一批用例，确认机制「真的在工作」而不只是「写在代码里」：

| 机制 | 开（默认） | 关（消融） |
|---|---|---|
| 保密闸门 · 召回通道（3 题） | **0/3 泄漏** | 3/3 泄漏 |
| 保密闸门 · 热窗通道（3 题） | **0/3 泄漏** | 3/3 泄漏 |
| 承诺通道（strict 段，3 条事实） | 段注入 / 3 条命中 | 段不注入 / 1 条命中 |
| 水位线（1000 token 下全量硬塞） | 556 token / 命中 0.2 / 丢段 60 | 1322 token / 命中 1.0 |

跨语料的一致性：在真实语料上，召回 + 结构（8000 预算）0.935 / 3395 token，全塞不裁剪 0.913 / 18957 token；机制方向与合成集一致，且真实数据上的差距更大。

## 10. 架构有效性验证

### 10.1 prompt 占用不随卡仓增长

26000 预算下，从 16 张卡到 200 张卡，prompt 大小几乎不变：

| 会话位置 | 已归档卡 | prompt token |
|---|---|---|
| t=50 | 16 | 2573 |
| t=100 | 40 | 2573 |
| t=200 | 73 | 2573 |
| t=300 | 106 | 2573 |
| t=400 | 150 | 2573 |
| t=499 | 200 | 3263（末尾 8 段未归档对话进入） |

预算降到 8000 也没有触发任何水位线（实际只用 3263）。这是「上下文有界」在真实数据上的直接证据：**卡仓扩大 12.5 倍，prompt 没有增长**。

### 10.2 保密闸门的真实暴露面

248 张真实卡中只有 2 张不是 `both`（1 张 `player`、1 张 `self`，都在大会话内）。按「第 t 轮的热窗 = `turn_end < t` 的卡倒序前 6 张」逐轮计算，修复前有 **23/497 轮（4.6%）** 会把这类卡原样注入【历史事件】；修复后为 0。比例不高，但性质是「把玩家知道的秘密讲给角色听」，一旦命中即为事故。这说明第 9 节的边界问题是真实数据里存在的问题，不是合成数据里的假想。

> 已知局限：`recent_cards(sid, cid, limit)` 不接受 `upto`，永远取库中最新 6 张，因此无法逐轮复现历史热窗，末轮 prompt 里不会出现那两张旧卡。线上 `upto` 恒为最新，不影响使用；但任何「回放历史某一轮」的用法都会拿到错误的热窗。

## 11. 评测中发现并修复的问题

评测不只产出数字，也暴露了三处实现缺陷，均已修复并补了回归用例：

1. **热窗通道绕过知识边界**：`retriever.retrieve` 会过滤 `knowledge_boundary=player`，但 `recent_cards` →【历史事件】只过滤可疑摘要，完全不看知识边界，只要这类卡落在最近 6 张就会被原样注入。已在 `_injectable()` 补上同一道过滤（复用 `retriever.ALLOW_PLAYER_BOUNDARY` 开关），并新增回归用例 R6b；修复后两条通道均为 0/3 泄漏。
2. **评测器把角色 id 写死**：`keyword_rank` / `hybrid_rank` / `prompt_text` 硬编码默认值 `shenqingwu`，`--cid jinyu` 未生效，首次跑真实语料时 46 条问句全部为 0。之前「加载器自测与内置 seed 一致」未发现，是因为自测恰好用的就是默认角色。已让三个函数接受 `cid`，并在外部语料模式下增加两道硬检查（会话不存在、问句 `gt` 不属于该会话都直接报错并列出副本中实际存在的会话与卡数），不再静默输出全 0。
3. **判分词表误伤**：短答与自然否定表达未被覆盖，导致边界题被误判为泄密。已改为逐题 rubric 判定，并对历史回答重判（不重新调用模型），原始值与修正值均保留（第 6 节）。

## 12. 已知限制

1. **真实语料规模小、标注单一**：46 条问句、一个会话、一位标注人，literal 占 56%，且没有 holdout 分层。0.891 应视为该会话上的自评上限，不是通用召回能力。
2. **合成语料偏简单**：30/60 张卡的剧本加向量后接近饱和（1.000），只能证明链路与机制有效，不代表真实聊天召回率。
3. **回答判分是启发式**：40 条题的 rubric 仍可能误伤；要更硬的结论需换模型判分或把题量扩到 200+。
4. **向量依赖外部服务**：SiliconFlow 不可用时静默退回关键词，真实语料召回会从 0.891 掉到 0.239，合成混淆集从 1.000 掉到 0.533。这是当前对真实体验影响最大的隐患，也是最该加本地兜底的地方。
5. **只覆盖中文文本**：语料全部为中文，且绑定单一角色人设；未验证其他语言、多角色、跨会话场景。
6. **单机单进程 SQLite**：未做多角色并发与写锁压测；同一 `RP_DB` 同时只允许一个进程。
7. **显著性机制尚未在真实数据上体现收益**：线上计数从本轮才上线，需要数周累积后重测。

## 13. 复现

```bash
# 回归测试（52 项，离线）
python tests/test_regression.py

# 合成集检索消融（离线，不需要任何 key）
python tools/eval_memory.py --corpus small --ablate
python tools/eval_memory.py --corpus scale --ablate

# 合成集 + 向量
RP_EMBED_KEY=... python tools/eval_memory.py --corpus scale

# 真实回答（≈50 次前台调用）
RP_FRONT_KEY=... RP_EMBED_KEY=... RP_FRONT_THINKING=off \
  python tools/eval_memory.py --real --out data/eval.json

# 真实回答 + 承重度（每题抽卡复问，≈100 次前台调用）
RP_FRONT_KEY=... RP_BACK_KEY=... RP_EMBED_KEY=... RP_FRONT_THINKING=off \
  python tools/eval_memory.py --real --ablate --out data/eval_ablate.json

# 外部基线 + 机制消融矩阵（离线，约 2 分钟）
python tools/eval_memory.py --corpus scale --ablate

# 真实语料（读线上库的只读副本，绝不写回线上）
python tools/eval_memory.py --cards-db data/memory.db --questions data/real_q.jsonl \
  --sid <线上 session_id> --cid jinyu

# 真实语料 + 消融（外部基线 / 水位线 / 保密闸门 / 显著性 / 承诺）
RP_EMBED_KEY=... python tools/eval_memory.py --cards-db data/memory.db \
  --questions data/real_q.jsonl --sid <线上 session_id> --cid jinyu --ablate
```

真实语料的两步准备：

```bash
# 1) 导出一份卡清单，方便人工写问句（评测本身直接读 memory.db 的只读副本）
sqlite3 data/memory.db ".mode json" \
  "SELECT event_id,session_id,character_id,turn_start,turn_end,summary,entity_hooks,
          knowledge_boundary,importance,mentions,verified FROM event_cards" > data/cards.json

# 2) 人工写问句（一行一条；gt=目标卡 event_id，snippet=那句唯一事实）
#    {"q":"客人为什么非要修这把伞","gt":"E2","snippet":"母亲留下的遗物","layer":"holdout"}
```

写问句时不能先看召回结果，否则就是自己考自己；literal / para / holdout 三档必须分开标注。

`--sid` / `--cid` 写错不会静默返回全 0，而是直接报错并列出副本中实际存在的会话。

CI 门槛：总体 `recall@4 ≥ 0.8`、holdout `≥ 0.7`（离线无 key 时的能力上限）。
